Mon rôle

Lead Product Manager & Product Designer

Mission freelance entre Merim et Autoya — pilotage produit et design d'une plateforme SaaS multi-tenant pour la restauration, du cadrage stratégique au design system code.

Plateforme multi-canal : app iOS opérationnelle (équipes terrain), panneau web administrateur (direction / franchise), backend Node / TypeScript et données PostgreSQL via Supabase. Périmètre : stratégie, segmentation, architecture data, design system, sécurité.

  • Stratégie & segmentation — distinction utilisateurs opérationnels (équipe, managers) vs acheteurs (rôle Payeur), offres à paliers (Starter / Premium / Franchise), parcours d'achat B2B.
  • Design system mobile — couleurs charte, surfaces, typographie custom « Jaguar Exuberant », jetons (espacements, rayons), pont Figma → SwiftUI documenté, prise en compte safe area et Dynamic Island.
  • Architecture produit — contrats TypeScript partagés (modèles, config API, événements WebSocket), enums métier en français dans le schéma base, Row Level Security côté Supabase.
  • Flows utilisateurs — biométrie sans sacrifier le login classique, filtres pills par restaurant, drill-down ventes, séparation canaux / DM (usages Slack-like), filtres croisés établissement × hashtag opérationnel.

Ce que je n'ai pas fait : l'intégralité du code (équipe dev mobile / web / back), les négociations partenaires (POS, livraison, réservation), la commercialisation.

Trois décisions

Les arbitrages qui ont façonné la plateforme

  1. 01

    Contrats TypeScript partagés entre iOS, web et API

    Premier réflexe sur un projet multi-canal : laisser chaque équipe (iOS, web, back) définir ses modèles, et synchroniser plus tard. Réalité : la dérive entre canaux est inévitable, et coûte plus cher à corriger en production qu'à prévenir.

    J'ai imposé une couche `shared/` en TypeScript — modèles, config API, événements WebSocket. Source unique consommée par le web admin, l'API, et alignée côté SwiftUI. Coût : discipline d'architecture, monorepo à maintenir. Bénéfice : zéro désync entre canaux, refacto de modèle propagée partout.

  2. 02

    Plans tarifaires inscrits dans le schéma, pas dans le marketing

    Tentation classique : définir les offres (Starter / Premium / Franchise) comme un attribut « marketing » et laisser l'application gérer les plafonds. Risque : utilisateurs Starter qui contournent les limites via API, dérogations custom par enseigne, monétisation érodée.

    J'ai inscrit les plafonds d'établissements (1 / 3 / sur mesure) dans les modèles partagés et dans le schéma PostgreSQL. Coût : couplage fort offre / data, évolution tarifaire = migration. Bénéfice : monétisation par construction, pas de contournement possible côté code.

  3. 03

    Locale française stricte, pas d'i18n générique

    Réflexe SaaS moderne : i18n dès le départ, anglais par défaut, français en seconde langue. Coût caché : un produit qui parle « anglais traduit », vocabulaire métier qui sonne faux pour les restaurateurs français.

    J'ai assumé un positionnement France / francophonie strict : enums métier en français dans le schéma base, formats EUR et locale fr_FR, vocabulaire opérationnel propre au métier (canaux, hashtags #shift / #affectation / #stock). Coût : pivot international = refonte data. Bénéfice : un produit qui parle juste à sa cible — pas de « traduit de l'américain ».

Impact

Ce que ça a livré

  • Plateforme multi-canal livrée : app iOS SwiftUI + panneau web admin + API Node / TypeScript + PostgreSQL via Supabase.
  • Modèles, config et événements partagés en TypeScript — zéro désync entre canaux, refactos propagées par construction.
  • Plans tarifaires (Starter / Premium / Franchise) ancrés dans le schéma — monétisation sans contournement.
  • Chat temps réel par établissement (WebSocket authentifié, diffusion par établissement, RLS Supabase) — confiance et isolation par construction.
  • Design system mobile documenté Figma → SwiftUI, police custom « Jaguar Exuberant », safe area et Dynamic Island pris en compte.
  • Locale FR native — enums métier, formats EUR / fr_FR, vocabulaire opérationnel propre à la restauration.
